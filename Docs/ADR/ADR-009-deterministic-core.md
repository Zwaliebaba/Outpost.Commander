# ADR-009 — The simulation reproduces on the same build

Status: **accepted** · 2026-10-08
Owns: same-binary-replay, tick-clock, simulation-prng, command-order, simulation-host

## Context

A bug is replayed from a seed and a command log on the build that made it. AGENTS.md R16 says that a simulation which replays is a deterministic core, whose rules are recorded in an ADR: no float where an integer will do, no unordered iteration that reaches the outcome, ticks as the only clock, and a pinned PRNG with a recorded seed.

A replay can promise the same binary, or also agreement across x64 and ARM64 ([ADR-003](ADR-003-x64-and-arm64.md)). The development machine is ARM64 and CI is x64. Only the server simulates ([ADR-002](ADR-002-authoritative-server.md)), so nothing in play needs two machines to agree.

## Decision

1. **A replay reproduces on the same binary** (owner, 2026-09-30). The same executable, or the same test DLL, given the same seed and the same commands at the same ticks, reaches the same state, bit for bit. No promise is made across x64 and ARM64, nor between Debug and Release, which are different binaries. Float results may differ: x64 and ARM64 can disagree wherever float code reaches the standard library's math functions or DirectXMath, which are implemented separately for each (R16).
2. **Floats are allowed for continuous quantities:** positions, headings and speeds. This is how R16's "no float where an integer will do" applies here. Under decision 1's promise a float gives the same result on every run of one binary, so an integer does no better for these. No result is promised across machines, so the simulation needs no fixed-point core. A quantity that is a count is an integer, including ticks, identifiers, Ore, and hit points, armor and damage as the tuning data holds them ([ADR-008](ADR-008-tuning-data.md)). In the simulation they count in hundredths, still as integers ([ADR-014](ADR-014-designs-and-combat.md) decision 3).
3. **The tick is the only clock.** `Neuron::TickHost` in `NeuronServer` is the one place elapsed wall time becomes ticks. The one other place wall time meets the simulation is a scheduled order's time of day, which the host makes a tick as its command arrives, before it is logged, so that the log replays ([ADR-080](ADR-080-events-and-scheduled-orders.md) decision 6). `InProcessServer` hands it the wall time that passed, from the server's own thread or from `Advance` in a test, and it runs the ticks that are due. It keeps the remainder exactly, as nanoseconds times ticks per second, so the rate does not drift. The rate is `rules.tickHz` from the tuning data, fixed for a match or a universe.
4. **Catch-up is capped at `MAX_TICKS_PER_ADVANCE`, five ticks per `Advance`.** After a longer stall, such as a debugger break or a dragged window, the backlog is dropped and the simulation resumes at its own pace. It does not race to catch up, and the command log still says which tick each command was applied at, so a replay is unaffected.
5. **Randomness is `Neuron::Random`:** xoshiro256\*\* 1.0 seeded through SplitMix64, written in `NeuronServer`, rather than `<random>`. `<random>`'s engines are specified by the standard, but its distributions are not, so the same seed could draw differently under another standard library. The generator is owned by the simulation and is part of its state. `RandomTests` pins its output against an independent implementation and the published test vector. A cold weapon's first shot draws from it, and so does the balance check's spread fire ([ADR-014](ADR-014-designs-and-combat.md)). The executable seeds each match from the system clock and writes the seed to the debugger output, in Debug and Release.
6. **Order is defined wherever it reaches the outcome.** Entities are held in identifier order, which is creation order. At the start of each tick the server applies the commands that arrived since the last one, at most `COMMANDS_PER_TICK`, 32, of each connection's, the rest waiting for the ticks after (owner, 2026-10-26), in the order of the server's connections, which is the order its seats were opened and its AI empires hosted, fixed before it starts, and then in the order each player sent them. A connection with more than `COMMANDS_WAITING_LIMIT`, 1,200, waiting is broken: the server closes a QUIC client's with `MalformedMessage` ([ADR-060](ADR-060-quic-in-process.md) decision 5), a loopback client's `Send` throws, and a hosted player's orders fail the server's thread ([ADR-025](ADR-025-server-thread.md) decision 5). No AI meets either: in the AI-against-AI matches of seeds 1 to 40 no seat gave more than 6 commands in a tick, and in three hour-long universes a deputy gave 25 at most, so those runs play the same with the limits as without ([the balance log](../Records/BalanceLog.md), 2026-10-26). It stamps each command with its connection's player, never the client's, and logs it with its tick, so the log replays in the same order. No unordered container is iterated in the simulation.
7. *(retired)*
8. **`Simulation` is the core, and `InProcessServer` is its host.** `Simulation` knows nothing of wall time, transports or clients. It takes a seed and a list of commands per tick, and it compares equal to another `Simulation` in the same state. `InProcessServer` owns it, the tick host, the connections and the command log. Which data files the server reads is [ADR-008](ADR-008-tuning-data.md) decision 7's.

## Consequences

- **A bug report needs the seed, the command log and the build.** A match's log lives in the server's memory; the seed in the debugger output and a test that replays the scenario do the job. A universe's log is written to its folder as each tick applies it, from its last save on, and the save and that log bring the universe back ([ADR-077](ADR-077-universe-state-on-disk.md)).
- **A replay made on the owner's ARM64 machine cannot be checked on CI's x64.** A replay test has to run the match and its replay in the same test run, as `ReplaysFromItsCommandLog` does.
- **A rejected command is told only to the player who gave it,** as an event in that player's snapshot, with no message of its own ([ADR-094](ADR-094-a-refused-command-is-told.md) decision 1).
- **A simulation without the tuning data,** as the movement and combat tests run, rejects the base's, research's and the designer's orders as not yet supported ([ADR-016](ADR-016-base-building.md)).

## What this forecloses

- Lockstep networking and replays shared between machines, without a new ADR that replaces floats in the core.
- `std::random_device`, `rand`, `<random>`'s distributions, wall-clock time and address-dependent values anywhere in `Simulation`.
